##### **1. `POST /api/attendance/scan`**
*   **HTTP Method:** `POST`
*   **Full Path:** `/api/attendance/scan`
*   **Purpose:** Records an employee's attendance (arrival or departure) based on a QR code scan. The first scan of the day is recorded as arrival, and the second as departure.
*   **Authentication Requirements:** Assumed to be authenticated (e.g., via JWT token).
*   **Path Parameters:** None
*   **Query Parameters:** None
*   **Request Body:**
    *   **Exact JSON Structure:**
        ```json
        {
            "userId": "string"
        }
        ```
    *   **Realistic Sample:**
        ```json
        {
            "userId": "a1b2c3d4-e5f6-7890-1234-567890abcdef"
        }
        ```
    *   **Field Validation Rules:**
        *   `userId`: Must be a valid UUID string.
*   **Expected Response Status Codes:**
    *   `200 OK`: Successful recording of arrival or departure.
    *   `400 Bad Request`: If `userId` is not a valid UUID format.
    *   `500 Internal Server Error`: If `userId` is unknown or already checked out today.
*   **Sample JSON Responses:**
    *   **Arrival:**
        ```json
        {
            "action": "ARRIVAL",
            "record": {
                "id": "abcde123-4567-8901-2345-67890abcdef0",
                "userId": "a1b2c3d4-e5f6-7890-1234-567890abcdef",
                "workDate": "2026-09-19",
                "arrivalTime": "2026-09-19T14:35:00.123456789",
                "departureTime": null,
                "workHours": 0.0
            },
            "totalPay": 0.0
        }
        ```
    *   **Departure:**
        ```json
        {
            "action": "DEPARTURE",
            "record": {
                "id": "abcde123-4567-8901-2345-67890abcdef0",
                "userId": "a1b2c3d4-e5f6-7890-1234-567890abcdef",
                "workDate": "2026-09-19",
                "arrivalTime": "2026-09-19T09:00:00.000000000",
                "departureTime": "2026-09-19T17:00:00.000000000",
                "workHours": 8.0
            },
            "totalPay": 120.50
        }
        ```

##### **2. `GET /api/attendance/today/{userId}`**
*   **HTTP Method:** `GET`
*   **Full Path:** `/api/attendance/today/{userId}`
*   **Purpose:** Retrieves the attendance record for a specific user for the current day.
*   **Authentication Requirements:** Assumed to be authenticated.
*   **Path Parameters:**

*   **Query Parameters:** None
*   **Request Body:** None
*   **Expected Response Status Codes:**
    *   `200 OK`: Returns the `AttendanceRecord` if found.
    *   `500 Internal Server Error`: If no record is found for today.
*   **Sample JSON Responses:**

        ```json
        {
            "id": "abcde123-4567-8901-2345-67890abcdef0",
            "userId": "a1b2c3d4-e5f6-7890-1234-567890abcdef",
            "workDate": "2026-09-19",

            "departureTime": "2026-09-19T17:00:00.000000000",
        ```

        ```json
        {
            "timestamp": "...", "status": 500, "error": "Internal Server Error",
        ```

### **Notes on Authentication and Validation**

**Authentication:**
The provided codebase does not explicitly include Spring Security annotations (like `@PreAuthorize`, `@Secured`, or configuration for JWT/OAuth2). However, for a real-world application, most endpoints (especially those involving data modification or retrieval of sensitive information) would require authentication. The current documentation assumes an authenticated context for most endpoints except for the user registration and customer account signup endpoints. Implementing robust authentication (e.g., using JWT tokens in headers) would be crucial for production.

**Validation:**
While some basic validation checks are present in the controllers (e.g., `userId` parsing to UUID, `name` not being blank), comprehensive input validation using Spring's `@Valid` annotation with JSR 303/349 (Bean Validation) annotations (like `@NotNull`, `@Size`, `@Email`, `@Min`, `@Max`) on DTOs and model classes is not explicitly visible in the controller code. The documentation assumes standard validation rules based on data types and common business requirements for the fields involved. For a production-grade application, server-side validation using these annotations would be highly recommended to ensure data integrity and prevent security vulnerabilities. The current error handling for validation issues primarily relies on `RuntimeException` or `IllegalArgumentException`, which would typically be caught by a `GlobalExceptionHandler` to return appropriate HTTP status codes (e.g., `400 Bad Request`).
